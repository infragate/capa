## Prioritized findings

### P1 — Validate the emitted edit, not just the input's serializability

**PR-introduced mismatch.** Reads and fresh writes use `@iarna/toml`; existing-file edits use `toml-patch` (`src/shared/capabilities.ts:448`, `:461`, `:532`). TOML **1.0 and 1.1 allow mixed arrays**. The installed iarna release documents **TOML 0.5**, whose array rules differ. This is a library/version restriction, not a general TOML limitation. Do not infer installed behavior from iarna's current default branch. Sources: [TOML 1.0 arrays](https://toml.io/en/v1.0.0#array), [TOML 1.1 arrays](https://toml.io/en/v1.1.0#array), [TOML 0.5 arrays](https://toml.io/en/v0.5.0#array), [iarna 2.2.5 README](https://github.com/iarna/iarna-toml/blob/v2.2.5/README.md). The patch library documents a broader TOML implementation and returns a string from its edit API: [official README](https://github.com/DecimalTurn/toml-patch), [official API](https://raw.githubusercontent.com/DecimalTurn/toml-patch/latest/docs/API.md).

Observed under Bun 1.4.4:

| Value | iarna fresh serialization | Patch output | iarna reload of patch |
| --- | --- | --- | --- |
| `[1, "two"]` | Throws mixed-types error | Writes mixed array | Rejects |
| `[1, 2.5]` | Writes `[1.0, 2.5]`; reload succeeds | Writes `[1, 2.5]` | Rejects integer/float mixture |
| `[[1], ["two"]]` | Succeeds | Succeeds | Succeeds |

The exported `appendCapabilityEntry` reproduces both failing reloads when appending an MCP tool with `def.defaults.filter` holding either of the first two arrays to `# original\nskills = []\ntools = []\n`. Thus a successful `TOML.stringify(data)` preflight alone misses the numeric case: the editor emits different literals. An existing `[1.0, 2.5]` array survived an unrelated patch and reloaded successfully.

**Refinement:** retain both libraries, check representation before serialization, then parse the **actual resulting string with the production iarna reader** and verify preservation of the intended values before `Bun.write`. Apply this to fresh writes and every mutation routed through `serializeStructuredCapabilities` (`src/shared/capabilities.ts:451`, `:644`, `:734`, `:807`, `:898`, `:943`). Reject incompatible output with a useful value path and library-specific explanation. Do not reject every array containing different JavaScript types or every nested array: supported numeric fresh writes and nested arrays must remain usable. No dependency replacement is necessary to meet the agreed fail-clearly contract.

### P1 — Meaningful configuration nulls require explicit rejection; optional nulls need preparation

**PR-introduced data-loss path; existing null semantics.** Iarna silently omits null-valued object fields and filters null array elements. Local examples: `{defaults:{filter:null}}` becomes an empty defaults table; `{args:[{default:null}]}` loses `default`; `[1,null,2]` becomes `[1,2]`. The fresh `writeCapabilitiesFile` also succeeds while dropping a tool's null default. Patch rejects these nulls before returning output; the exported append reproduction leaves the original file intact. Sources: [versioned iarna writer](https://github.com/iarna/iarna-toml/blob/v2.2.5/stringify.js), repository call sites above.

TOML has no null value, including in 1.1: [official value types](https://toml.io/en/v1.1.0#keyvalue-pair). This is a language restriction. However, capa already distinguishes absent optional fields from meaningful arbitrary tool data. `stripNulls` preserves complete `default`/`defaults` subtrees and retains array positions (`src/shared/capabilities.ts:383`, `:397`; already present at `upstream/main:src/shared/capabilities.ts:381`, `:395`). Existing tests explicitly preserve null tool defaults (`src/shared/__tests__/capabilities.test.ts:284`). A lock comparison rule must not erase them.

**Refinement:** prepare optional null fields according to existing configuration semantics before calling either writer; recursively reject remaining meaningful nulls, including inside arrays and arbitrary defaults, with paths such as `tools[0].def.defaults.filter`. Do not blanket-reject optional `description: null`: fresh writing currently omits it, whereas patch rejects it, so unprepared edits violate the agreed optional-null behavior. Do not apply the lock comparator's null-dropping policy to configuration values. Preserve raw document structure/comments rather than replacing it wholesale with schema-defaulted configuration data.

Compute and verify output before opening the destination for writing. The current argument evaluation already prevents a serialization exception from reaching `Bun.write`; it does not catch successful lossy serialization. [Bun's file-I/O documentation](https://bun.sh/docs/runtime/file-io) documents the APIs in use. This finding concerns representation failures; it makes no Node-derived claim of crash-safe or atomic filesystem replacement.

### P1 — Keep content-based active-lock reads, but strengthen the current sniffer

**PR-introduced heuristic.** `src/shared/lockfile.ts:310` recognizes TOML only when trimmed text starts with `version =` or contains selected array-of-table headers. Bun repros show valid empty TOML locks starting with a comment or `generator =` are misclassified as YAML and fail loading. Conversely, valid YAML containing `generator: "[[skills]]"` is misclassified as TOML. TOML object-key order is not guaranteed: [official table semantics](https://toml.io/en/v1.0.0#table).

**Refinement:** retain content-based parsing at the **single active path**, independent of the newly selected configuration format. Use parser-backed recognition with lock-schema validation, or a defensible sniff with validated fallback; do not inspect unrelated paths to recover from a parse failure. Include commented/reordered TOML, empty sections, provider-only locks, and marker text inside YAML strings. A format switch in the same directory keeps the extensionless lock's path, so assuming the new configuration's format would lose readable old pins (`src/shared/lockfile.ts:44`, `:407`). Upstream already recognized JSON by content and otherwise read YAML (`upstream/main:src/shared/lockfile.ts:219`).

### P2 — Separate lock comparison normalization from typed decoding

**Retain decision; avoid an incomplete simplification.** Both upstream and HEAD use order-sensitive `JSON.stringify` for semantic identity (`upstream/main:src/shared/lockfile.ts:243`; `src/shared/lockfile.ts:438`). Bun repros return unequal keys for reordered object fields and null-versus-missing fields. Recursive object-key sorting and omission of null-valued **object fields**, while preserving array order/elements, addresses this. Keep the existing semantic payload, including provider ownership records (`src/shared/lockfile.ts:427`).

But removing restoration without replacing typed decoding drops valid TOML pins: `isNullableString(undefined)` is false, and the validators require nullable fields (`src/shared/lockfile.ts:81`, `:171`, `:188`, `:205`). A skill missing `requestedRef` fails the exported validator in the repro. The current TOML reader restores fields before validation (`:323`). These fields represent absent metadata in the lock schema (`src/types/lockfile.ts:31`, `:53`, `:89`), unlike meaningful tool defaults.

**Refinement:** remove field-order tables used solely for equality. Retain schema-aware decoding of omitted nullable TOML fields into the existing `string | null` in-memory types, rejecting wrong non-null types and requiring non-null pin fields. Schema knowledge cannot disappear merely because comparison is generic. Keep upstream's validation policy: malformed entries are warned about and skipped, while top-level schema failures throw (`upstream/main:src/shared/lockfile.ts:141`, `:162`; HEAD `:243`, `:264`). Changing every invalid entry into a fatal error would be a separate behavior change. The shared decoder and canonical semantic key should serve save comparisons and fingerprints; fingerprinting already shares `loadLockfile` upstream (`src/shared/install-fingerprint.ts:26`, unchanged from baseline).

### P2 — Require both semantic equality and matching output format to skip a save

**Existing shortcut, newly relevant format requirement.** `saveLockfile` skips on semantic equality without checking disk format (`src/shared/lockfile.ts:453`; same shortcut at `upstream/main:src/shared/lockfile.ts:258`). A Bun repro writes a YAML lock, calls `saveLockfile(project, sameLock, "toml")`, and confirms it remains YAML. Keep the agreed explicit format-change rewrite. Choose the desired format from the winning configuration candidate, not a separate JSON-exists test or the current always-TOML function (`src/shared/paths.ts:135`; `src/shared/lockfile.ts:55`). Matching format preserves upstream's intent (`upstream/main:src/shared/lockfile.ts:38`) while extending discovery.

**Refinement:** skip only when disk format matches the requested format **and** canonical semantics match. Format-only conversion should preserve `generator` and `generatedAt`; the existing builder restamps them only for semantic changes (`src/shared/lockfile.ts:542`, `:732`; same policy upstream at `:344`, `:534`). Retain `generator` in fingerprints, as agreed and already implemented upstream; do not stamp the current executable version during every load/save or exclude this field casually. Missing/non-string generator fallback to the running version is existing validation behavior (`src/shared/lockfile.ts:292`; upstream `:190`), not a new guarantee of cross-version identity for malformed metadata.

### P2 — Read-only lock selection must also cover fingerprint reads and empty-install cleanup

**Retain decision; remove PR side effects at every entry point.** HEAD migrates/deletes unrelated locks during `loadLockfile` (`src/shared/lockfile.ts:356`, `:411`). Because fingerprinting calls this reader, a status/fingerprint operation can also mutate locks. Upstream loading returned null for a missing active lock and performed no migration (`upstream/main:src/shared/lockfile.ts:208`). The install task additionally deletes every candidate when the built lock is empty (`src/cli/commands/install-tasks/write-lockfile.ts:45`); upstream deleted only its one active root lock (`upstream/main:src/cli/commands/install-tasks/write-lockfile.ts:43`). Restrict empty-install cleanup to the winning configuration's lock. No fallback, read-side conversion, or orphan deletion is needed. The existing typed lock schema has no meaningful mixed arrays and its nullable metadata can be omitted on TOML disk and restored on read, so retaining iarna is practical (`src/types/lockfile.ts:20`, `:110`, `:126`).

## Bun native API boundary and focused verification

Current [official Bun TOML reference](https://bun.sh/reference/bun/TOML) includes **both parse and stringify**. Local Bun 1.4.4 exposes both; native stringify accepts `[1,"two"]` and rejects null. However, the [Bun 1.3.14 declarations](https://github.com/oven-sh/bun/blob/bun-v1.3.14/packages/bun-types/bun.d.ts#L739) expose only TOML parse. This is versioned source evidence, not a native-runtime test on 1.3.14. Current documentation/local capability is insufficient grounds to introduce native stringify into CI's supported baseline. Keep existing dependencies and runtime; no native migration is needed for these findings.

Reproductions ran as temporary Bun scripts importing the actual installed libraries and repository exports; fixture directories were under `/tmp` and removed afterward. No full test suite or Bun 1.3.14 execution was performed. Implementation verification should run the cases above on CI's pinned runtime, plus: optional-null edits; meaningful-null rejection with unchanged bytes; valid-edit comment retention; cross-format lock round trips with skill/plugin/hook nullable fields; active-lock-only reads/cleanup with malformed unrelated locks; unchanged-pin format conversion; stable timestamp/key-order/null-metadata identity; changed pins, generator, provider values, and array order remaining detectable. These are focused refinements to the agreed decisions, not a broader serialization refactor.
