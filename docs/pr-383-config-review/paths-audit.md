# PR #383 path/upload audit

The agreed direction is sound, with two wrap integration constraints to settle before implementation: distinguish the trusted source root from the output root, and keep nested shadow locks private. Current-directory/explicit-path root selection is fixed; no ancestor discovery or monorepo inheritance is proposed.

**Evidence boundary.** Compared working `HEAD` (`1d35b3b`) with `git show upstream/main:<file>` at `d7af119`. The research worker's remote refresh failed because its sandbox lacked network access; the parent session successfully refreshed upstream `main` during this audit and confirmed the same commit. Audited [decisions:10–21](decisions.md#L10). Small `/tmp` reproductions imported the actual project modules under **Bun 1.4.4, Linux x64**; fixture directories were removed. CI pins **Bun 1.3.14** across Linux, Windows and macOS ([test.yml:15–17](../../.github/workflows/test.yml#L15)); these are not CI-version or native Windows/macOS results. No Node watcher guarantees are assumed. Watchers and lock serialization/comparison are outside this path/upload audit.

## Prioritized findings

### P1 — New nested lock placement bypasses wrap's existing isolation

**PR regression.** Upstream's lock is always `<project>/capabilities.lock` (`upstream/main:src/shared/lockfile.ts:29–30`), and wrap excludes that top-level name. The PR selects the winning configuration's directory ([lockfile.ts:44–48](../../src/shared/lockfile.ts#L44)). Wrap still links ordinary top-level entries, including `.config`, into the real checkout; its exclusions cover the root lock, `.capa` and provider-owned entries ([symlink-workspace.ts:23–35,145–158](../../src/cli/utils/wrap/symlink-workspace.ts#L23)). Thus `shadow/.config/capa/capabilities.lock` shares the real lock's storage. Saving uses `Bun.write`; empty-lock cleanup removes the selected path ([lockfile.ts:458–469](../../src/shared/lockfile.ts#L458), [write-lockfile.ts:52–64](../../src/cli/commands/install-tasks/write-lockfile.ts#L52)). Removing migration alone does not fix this.

**Reproduction:** with the PR's currently supported `.config/capabilities/config.yaml`, `buildSymlinkWorkspace()` made `shadow/.config` a symlink. `getLockfilePath(shadow)` returned the nested shadow lock; `Bun.write()` there created the real project's nested lock. Renaming `capabilities` to `capa` leaves the same topology. This establishes the write-through mechanism, without running a full install.

**Refinement:** preserve a private, co-located lock in the shadow for both `.config/capabilities.*` and `.config/capa/config.*`. Materialize the active configuration's directory chain in the shadow, linking source/config/assets selectively and keeping the lock an independent file. Include existing warm shadows in repair; current repair checks provider paths, then restores ordinary top-level links ([validate-shadow-workspace.ts:60–93](../../src/cli/utils/wrap/validate-shadow-workspace.ts#L60)). Merely excluding `.config` would hide configuration and assets. Verify real-lock bytes remain unchanged after shadow install, save and empty-lock cleanup. Limit this work to the new nested-lock regression; broader wrap isolation is separate.

### P1 — Agent containment needs an explicit trusted source root through both call chains

**Agreed extension plus hardening, not existing containment.** Upstream and HEAD use `assertSafeRepoPath(dirname(config), path)` for both agent base and snippets ([install.ts:222–236,340–355](../../src/cli/utils/agents-file/install.ts#L222)). That shared helper rejects every `..` segment but checks only lexical containment ([repo-file.ts:41–82](../../src/shared/repo-file.ts#L41)). Bun reproduction rejected `../../docs/team.md`, yet a project-local `escape/outside.md` symlink successfully read an external file into generated `AGENTS.md`. Realpath enforcement therefore intentionally tightens an inherited loophole while enabling project-local parent paths. Rules remain different: upstream and HEAD use unrestricted `resolve(configDir, rule.path)` and read it ([install-rules.ts:48–57](../../src/cli/commands/install-tasks/install-rules.ts#L48)); Bun confirmed external relative and absolute rule reads.

A realpath check against the **shadow output root** would reject valid agent sources: shadow `docs` and `.config` resolve into the real checkout. There are two call chains:

- CLI wrap passes `projectPath: shadow`, `identityPath: real` ([workspace.ts:235–249](../../src/cli/utils/wrap/workspace.ts#L235)); install discovers the config through the shadow and currently passes only that config path and output root into the agent installer ([install.ts:152–179](../../src/cli/commands/install.ts#L152), [install-agent-instructions.ts:23–29](../../src/cli/commands/install-tasks/install-agent-instructions.ts#L23)).
- Server sync retains the **real** configuration path while replacing `projectPath` with the shadow output path ([sync-project-artifacts.ts:169–177,498–509](../../src/server/sync-project-artifacts.ts#L169)). Deriving the project root from the config directory also fails for nested configs.

**Minimal call-chain refinement:** carry an explicit trusted source-project path into the agent read context, defaulting to the normal project root. Retain the explicit real identity/source path in CLI install context and pass it through the agent task; in server shadow sync preserve the original project path before overriding the output path. Resolve authored relative paths against the selected configuration directory, then compare the existing source's realpath with the canonical trusted source root. Keep writes and the existing source/output self-reference guard tied to the output root ([source-guard.ts:9–40](../../src/cli/utils/agents-file/source-guard.ts#L9)). Do not infer trust from whichever external target a symlink happens to reach.

Preserve the existing rejection of absolute/drive-prefixed agent references; allowing `..` does not require accepting them. Do not relax the shared remote-repository helper or apply agent containment to legacy rules. Do not reuse `isPathInside` unchanged for security: its `startsWith('..')` rejects valid `..notes` names and lacks an absolute-relative-result check for different Windows drives ([paths.ts:59–63](../../src/shared/paths.ts#L59)). Bun's `path.win32.relative('C:\\project', 'D:\\outside')` returned an absolute drive path; this is a library reproduction, not native Windows filesystem validation.

### P2 — Browse translation must occur exactly once, only when selecting

**New integration requirement.** Listing returns project-relative navigation paths ([project-routes.ts:416–422](../../src/server/project-routes.ts#L416)). The picker currently forwards those directly for file, directory-click and keyboard selection, while upload already returns a stored path ([LocalPathPicker.tsx:67–76,161–197](../../web-ui/src/features/projects/components/LocalPathPicker.tsx#L67)). Manual input already represents the authored stored path. Inline agent-base creation separately uploads and saves the returned path ([BaseDialog.tsx:52–63](../../web-ui/src/features/projects/components/agents/BaseDialog.tsx#L52)).

**Refinement:** use the shared server-side stored-path conversion for the selected project-relative path and kind, with the active configuration context. Keep navigation paths unchanged. Cover every selection handler; do not convert upload responses, manual text, existing authored paths or subsequent mutation requests again. A second conversion would add another parent traversal to an already-correct rule/instruction path. No browser-side duplicate path arithmetic is needed.

### P2 — Browse cannot currently reach the new upload folders through its UI

**Inherited filter, newly relevant destination.** Both upstream (`src/server/project-fs.ts:171–172`) and HEAD skip all dot-prefixed entries ([project-fs.ts:180–181](../../src/server/project-fs.ts#L180)). The picker always starts at the root and has no directory-address field ([LocalPathPicker.tsx:45–65,134–143](../../web-ui/src/features/projects/components/LocalPathPicker.tsx#L45)). Bun root listing omitted `.config`, so users cannot browse into newly uploaded assets there.

**Refinement:** explicitly include `.config` in project navigation while retaining containment and the other hidden-entry rules. If intentionally deferred, record that Browse cannot select those assets; stored-path translation alone does not make them reachable. Avoid expanding this into a general hidden-files browser. An inherited edge case also remains: a visible external symlink makes root listing fail during `toProjectRelative` before symlink entries are skipped ([project-fs.ts:183–195](../../src/server/project-fs.ts#L183)); Bun reproduced rejection rather than external selection. Preserve the project boundary without promising flawless baseline symlink navigation.

### P2 — Upload conversion mixes logical and physical path bases

**PR regression for symlinked project roots.** `mkdirInsideProject` returns a physical path, while the new `pathStoredInCapabilities` computes relative paths against unresolved logical project/config paths ([project-fs.ts:128–154,248–256](../../src/server/project-fs.ts#L128), [project-uploads.ts:63–75](../../src/shared/project-uploads.ts#L63)). Upstream returned `toProjectRelative`, which canonicalizes both sides (`upstream/main:src/server/project-fs.ts:78–101,229–232`).

**Reproduction:** uploading a rule through `alias -> real` produced `../../../real/.config/capabilities/rules/new.md` instead of `rules/new.md`. It reaches the file on that machine, but unnecessarily embeds the checkout's external directory name and breaks portability. Skills use the same mixed-base helper.

**Refinement:** calculate stored relative paths using consistent physical bases for a symlinked root, retaining the selected logical configuration location as the authored base. Detect the winning configuration once per upload and use that same selection for destination and conversion; HEAD independently discovers it in the destination helper and again in the upload ([paths.ts:214–223](../../src/shared/paths.ts#L214), [project-fs.ts:240–241](../../src/server/project-fs.ts#L240)). This removes contradictory bases if the winner changes between those calls; it does not make a later UI save atomic with an upload.

### P2 — Wrap identity must include the selected configuration location

**New discovery interaction.** Upstream and HEAD fingerprint config text without its path ([workspace.ts:73–96](../../src/cli/utils/wrap/workspace.ts#L73)); HEAD's new locations allow identical text to have different local rule/instruction bases. Bun reproduction moved identical bytes from `capabilities.yaml` to `.config/capabilities/config.yaml`, with no locks present: both fingerprints were `0c5fbe7139f5`. A warm workspace with an unchanged fingerprint can skip install ([workspace.ts:304–338](../../src/cli/utils/wrap/workspace.ts#L304)), leaving materialized content from the old base.

**Refinement:** include the winning config's project-relative location in wrap identity alongside its text. This is a path-dependent invalidation fix, separate from the agreed lock semantic comparison. Cover an equal-content location switch; do not expand this into recursive source-content fingerprinting.

## Confirmed constraints and scope boundaries

- **Root selection is already correct.** Upstream and HEAD use cwd or the explicit path (`upstream/main:src/cli/commands/install.ts:61–76`). Discovery order root → `.config` → `.config/capa`, TOML → YAML → JSON is the agreed **PR** behavior, not upstream behavior: upstream only discovers root YAML/JSON and errors if both exist (`upstream/main:src/shared/paths.ts:89–113`). Keep `init` at the project root ([paths.ts:158–164](../../src/shared/paths.ts#L158)). `.config/capa` is project-local, not the user's XDG config directory.
- **Keep all three bases visible in implementation:** project root for identity, output and local skills; selected config directory for local rules/instructions; trusted real source root for agent containment during wrap. CLI local-skill install and server preview already agree on the project-root base ([install-one-skill.ts:97–105](../../src/cli/commands/install-tasks/helpers/install-one-skill.ts#L97), [skill-content.ts:309–318](../../src/server/skill-content.ts#L309)); both consumers are unchanged from upstream. Server command execution remains project-based, too ([tool-executor.ts:262–263](../../src/server/tool-executor.ts#L262), [subprocess-manager.ts:136](../../src/server/subprocess-manager.ts#L136)). Do not rebase them to `.config` as part of discovery.
- **No migration is the right boundary.** Remove the upload-time migrator call and its move/rewrite machinery ([project-fs.ts:227](../../src/server/project-fs.ts#L227), [project-uploads.ts:185–245](../../src/shared/project-uploads.ts#L185)). Leaving existing references untouched does not automatically preserve their meaning when a user manually moves a config: config-relative rules/agents then require manual rebasing; project-relative skills do not. Do not add automatic relocation, reference repair or legacy-directory discovery fallback. Also, wrap's top-level `.capa` exclusion predates this PR; old `.capa/imports` references being absent in a shadow is an inherited limitation, not a reason to restore migration.

Expected paths for **new** uploads after the rename (skills are stored project-relative; rules and agents use the final column):

| Winning configuration | Physical upload directory for kind | Stored rule/instruction prefix |
| --- | --- | --- |
| `capabilities.*` or no config | `.capa/imports/` | `.capa/imports/` |
| `.config/capabilities.*` | `.config/capa/{kind}/` | `capa/{kind}/` |
| `.config/capa/config.*` | `.config/capa/{kind}/` | `{kind}/` |

Bun confirmed that selecting `docs/team.md` against `.config/capa/config.yaml` yields `docs/team.md` for skills and `../../docs/team.md` for rules/instructions using the existing conversion helper. Verify the refinements with focused root/nested-config, symlink-root, shadow-source, private-shadow-lock and Browse-selection cases on CI's pinned Bun/platform matrix. No runtime upgrade or broader path-policy rewrite is needed.
